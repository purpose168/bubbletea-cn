# Bubble Tea CN 开发规范

## 概述

本文档定义了 Bubble Tea CN 项目的开发规范，包括编码规范、命名规范、代码审查标准及文档编写规范。

## 编码规范

### Go 代码规范

遵循 Go 官方代码规范和 Effective Go 指南。

#### 格式化

使用 `go fmt` 格式化代码：

```bash
go fmt ./...
```

#### 导入顺序

导入包按以下顺序分组：

1. 标准库
2. 第三方库
3. 项目内部包

每组之间用空行分隔：

```go
import (
    "context"
    "fmt"
    "os"
    
    "github.com/muesli/cancelreader"
    
    "github.com/purpose168/bubbletea-cn"
)
```

#### 命名规范

##### 包名

- 使用小写字母
- 简短、有意义
- 避免下划线和驼峰命名

```go
// 好的包名
package tea
package renderer
package key

// 不好的包名
package bubbleTea
package tea_renderer
```

##### 接口名

- 单方法接口使用方法名 + "er" 后缀
- 多方法接口使用描述性名称

```go
// 单方法接口
type Reader interface {
    Read([]byte) (int, error)
}

type Writer interface {
    Write([]byte) (int, error)
}

// 多方法接口
type Model interface {
    Init() Cmd
    Update(Msg) (Model, Cmd)
    View() string
}
```

##### 常量名

- 使用驼峰命名法
- 导出常量首字母大写
- 私有常量首字母小写

```go
// 导出常量
const (
    KeyEnter = iota
    KeyEscape
    KeySpace
)

// 私有常量
const (
    defaultFPS = 60
    maxRetries = 3
)
```

##### 变量名

- 使用驼峰命名法
- 导出变量首字母大写
- 私有变量首字母小写
- 避免缩写，除非是广泛接受的缩写

```go
// 导出变量
type Program struct {
    InitialModel Model
    Output       io.Writer
}

// 私有变量
type Program struct {
    msgs      chan Msg
    errs      chan error
    finished  chan struct{}
}
```

##### 函数名

- 使用驼峰命名法
- 导出函数首字母大写
- 私有函数首字母小写
- 函数名应该描述函数的行为

```go
// 导出函数
func NewProgram(model Model, opts ...ProgramOption) *Program {
    return &Program{
        initialModel: model,
    }
}

// 私有函数
func (p *Program) initTerminal() error {
    // 实现
}
```

#### 错误处理

- 总是检查错误
- 使用 `errors.New()` 创建简单错误
- 使用 `fmt.Errorf()` 创建带上下文的错误
- 使用 `errors.Is()` 和 `errors.As()` 检查错误

```go
// 检查错误
file, err := os.Open("file.txt")
if err != nil {
    return fmt.Errorf("failed to open file: %w", err)
}

// 创建错误
var ErrInvalidInput = errors.New("invalid input")

// 检查错误
if errors.Is(err, ErrInvalidInput) {
    // 处理无效输入
}
```

#### 并发

- 使用 goroutine 执行并发任务
- 使用 channel 进行通信
- 使用 `sync.WaitGroup` 等待 goroutine 完成
- 使用 `context.Context` 管理 goroutine 生命周期

```go
// 使用 goroutine
go func() {
    defer close(ch)
    
    for {
        select {
        case <-ctx.Done():
            return
        case msg := <-msgs:
            ch <- process(msg)
        }
    }
}()

// 使用 WaitGroup
var wg sync.WaitGroup
for i := 0; i < n; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        // 执行任务
    }()
}
wg.Wait()
```

#### 注释规范

- 导出的类型、函数、常量必须有注释
- 注释以名称开头
- 注释应该描述"是什么"，而不是"怎么做"
- 使用完整的句子

```go
// Model 包含程序的状态以及其核心函数。
type Model interface {
    // Init 是第一个被调用的函数，返回可选的初始命令。
    Init() Cmd
    
    // Update 在收到消息时被调用，用于检查消息并更新模型。
    Update(Msg) (Model, Cmd)
    
    // View 渲染程序的 UI，返回一个字符串。
    View() string
}

// NewProgram 创建一个新的程序实例。
func NewProgram(model Model, opts ...ProgramOption) *Program {
    return &Program{
        initialModel: model,
    }
}
```

### 文件组织

#### 文件命名

- 使用小写字母
- 使用下划线分隔单词
- 文件名应该描述文件的内容

```
tea.go
renderer.go
key.go
mouse.go
```

#### 文件结构

每个文件应该包含相关的功能：

```go
// tea.go
package tea

// 导出类型
type Program struct { ... }

// 导出函数
func NewProgram(model Model, opts ...ProgramOption) *Program { ... }

// 私有函数
func (p *Program) initTerminal() error { ... }
```

### 测试规范

#### 测试文件命名

- 测试文件名与被测试文件名相同，加上 `_test.go` 后缀

```
tea.go → tea_test.go
key.go → key_test.go
```

#### 测试函数命名

- 测试函数名以 `Test` 开头
- 测试函数名应该描述被测试的功能

```go
func TestNewProgram(t *testing.T) {
    // 测试 NewProgram 函数
}

func TestProgram_Run(t *testing.T) {
    // 测试 Program.Run 方法
}
```

#### 表格驱动测试

使用表格驱动测试来测试多个用例：

```go
func TestKeyString(t *testing.T) {
    tests := []struct {
        name string
        key  Key
        want string
    }{
        {
            name: "enter key",
            key:  Key{Type: KeyEnter},
            want: "enter",
        },
        {
            name: "escape key",
            key:  Key{Type: KeyEscape},
            want: "esc",
        },
    }
    
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            if got := tt.key.String(); got != tt.want {
                t.Errorf("Key.String() = %v, want %v", got, tt.want)
            }
        })
    }
}
```

## 命名规范

### 项目命名

- 项目名使用小写字母
- 使用连字符分隔单词
- 项目名应该描述项目的功能

```
bubbletea-cn
bubbles-cn
```

### 模块命名

- 模块名使用小写字母
- 使用下划线分隔单词
- 模块名应该描述模块的功能

```
renderer
inputreader
standard_renderer
```

### 消息命名

- 消息名使用描述性名称
- 以 `Msg` 结尾表示消息类型
- 以 `Msg` 结尾表示消息实例

```go
// 消息类型
type KeyMsg Key
type MouseMsg MouseEvent

// 消息实例
type QuitMsg struct{}
type SuspendMsg struct{}
```

### 命令命名

- 命令函数名使用动词
- 命令应该描述执行的操作

```go
func Quit() Msg
func Suspend() Msg
func ClearScreen() Msg
func EnterAltScreen() Msg
```

## 代码审查标准

### 审查清单

#### 功能性

- [ ] 代码实现了预期的功能
- [ ] 边界条件得到正确处理
- [ ] 错误处理完善
- [ ] 并发安全

#### 可读性

- [ ] 代码易于理解
- [ ] 变量和函数命名清晰
- [ ] 注释充分且准确
- [ ] 代码结构合理

#### 性能

- [ ] 算法复杂度合理
- [ ] 没有不必要的内存分配
- [ ] 没有不必要的计算
- [ ] 没有性能瓶颈

#### 安全性

- [ ] 没有安全漏洞
- [ ] 输入验证充分
- [ ] 没有敏感信息泄露
- [ ] 资源正确释放

#### 测试

- [ ] 单元测试覆盖充分
- [ ] 测试用例完整
- [ ] 测试通过

### 审查流程

1. 提交 Pull Request
2. 至少一名维护者审查代码
3. 审查者提出修改意见
4. 作者修改代码
5. 审查通过后合并

### 审查意见

- 提供建设性的反馈
- 解释为什么需要修改
- 提供修改建议
- 保持礼貌和专业

## 文档编写规范

### 代码注释

#### 包注释

每个包都应该有注释，描述包的功能：

```go
// Package tea 提供了一个基于 The Elm Architecture 的 TUI 框架。
//
// Bubble Tea 是一个用于构建终端用户界面的小型框架，灵感来自
// The Elm Architecture。它非常适合构建复杂的交互式应用。
package tea
```

#### 类型注释

导出的类型必须有注释：

```go
// Program 是 Bubble Tea 的核心结构，管理整个应用程序的生命周期。
type Program struct {
    initialModel Model
    msgs         chan Msg
    // ...
}
```

#### 函数注释

导出的函数必须有注释：

```go
// NewProgram 创建一个新的程序实例。
//
// 参数:
//   - model: 初始模型
//   - opts: 程序选项
//
// 返回:
//   - *Program: 新的程序实例
func NewProgram(model Model, opts ...ProgramOption) *Program {
    return &Program{
        initialModel: model,
    }
}
```

## 版本控制

### 分支策略

- `main`: 主分支，保持稳定
- `develop`: 开发分支
- `feature/*`: 功能分支
- `bugfix/*`: 修复分支
- `release/*`: 发布分支

### 提交信息

使用清晰的提交信息：

```
<type>(<scope>): <subject>

<body>

<footer>
```

类型：
- `feat`: 新功能
- `fix`: 修复
- `docs`: 文档
- `style`: 格式
- `refactor`: 重构
- `test`: 测试
- `chore`: 构建/工具

示例：

```
feat(renderer): 添加 ANSI 压缩功能

添加 ANSI 压缩功能以减少输出大小，提高性能。

Closes #123
```

## 性能优化

### 渲染优化

- 只渲染变化的部分
- 使用帧率控制
- 压缩 ANSI 序列

### 内存优化

- 重用缓冲区
- 避免不必要的内存分配
- 及时释放资源

### 并发优化

- 使用 goroutine 并发处理
- 使用 channel 通信
- 避免锁竞争

## 安全规范

### 输入验证

- 验证所有输入
- 处理边界条件
- 防止缓冲区溢出

### 资源管理

- 及时关闭文件
- 及时释放资源
- 正确处理错误

### 敏感信息

- 不要记录敏感信息
- 不要在日志中输出密码
- 使用环境变量存储敏感信息

## 总结

遵循这些开发规范可以确保代码质量、可维护性和可扩展性：

1. **代码规范**: 遵循 Go 官方规范
2. **命名规范**: 使用清晰的命名
3. **代码审查**: 确保代码质量
4. **文档编写**: 提供充分的文档
5. **性能优化**: 保持高性能
6. **安全规范**: 确保安全性

这些规范有助于团队协作和项目维护。
