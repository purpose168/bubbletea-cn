# Bubble Tea CN 版本控制策略

## 概述

本文档定义了 Bubble Tea CN 项目的版本控制策略，包括分支管理策略、代码合并流程及版本号命名规则。

## 分支管理策略

### 分支类型

#### main 分支

- **用途**: 主分支，保持稳定
- **状态**: 始终可部署
- **保护**: 启用分支保护
- **合并**: 只接受来自 develop 或 release 分支的合并请求

#### develop 分支

- **用途**: 开发分支，集成最新功能
- **状态**: 相对稳定
- **合并**: 接受来自 feature 和 bugfix 分支的合并请求

#### feature 分支

- **用途**: 开发新功能
- **命名**: `feature/<功能名>`
- **来源**: 从 develop 分支创建
- **目标**: 合并到 develop 分支

#### bugfix 分支

- **用途**: 修复 bug
- **命名**: `bugfix/<问题描述>`
- **来源**: 从 develop 或 main 分支创建
- **目标**: 合并到 develop 或 main 分支

#### release 分支

- **用途**: 准备发布
- **命名**: `release/<版本号>`
- **来源**: 从 develop 分支创建
- **目标**: 合并到 main 和 develop 分支

#### hotfix 分支

- **用途**: 紧急修复生产问题
- **命名**: `hotfix/<问题描述>`
- **来源**: 从 main 分支创建
- **目标**: 合并到 main 和 develop 分支

### 分支流程图

```
main (生产)
    │
    ├── hotfix/* → main
    │              ↓
    │           develop (开发)
    │              │
    │              ├── feature/* → develop
    │              │
    │              ├── bugfix/* → develop
    │              │
    │              └── release/* → main
    │                             ↓
    │                          develop
```

## 代码合并流程

### Pull Request 流程

#### 1. 创建分支

```bash
# 从 develop 创建功能分支
git checkout develop
git pull origin develop
git checkout -b feature/new-feature
```

#### 2. 开发和提交

```bash
# 添加文件
git add .

# 提交代码
git commit -m "feat: 添加新功能"

# 推送到远程
git push origin feature/new-feature
```

#### 3. 创建 Pull Request

- 在 GitHub/GitLab 上创建 Pull Request
- 选择目标分支（通常是 develop）
- 填写 PR 描述
- 关联相关 Issue

#### 4. 代码审查

- 至少一名维护者审查代码
- 审查者提出修改意见
- 作者修改代码
- 审查通过后合并

#### 5. 合并代码

```bash
# 使用 squash merge
git checkout develop
git merge --squash feature/new-feature
git commit -m "feat: 添加新功能"

# 删除分支
git branch -d feature/new-feature
git push origin --delete feature/new-feature
```

### 合并策略

#### Squash Merge

- **用途**: 功能分支合并到 develop
- **优点**: 保持历史清洁
- **缺点**: 丢失提交历史

```bash
git merge --squash feature/new-feature
```

#### Merge Commit

- **用途**: release 分支合并到 main
- **优点**: 保留完整历史
- **缺点**: 历史可能变得复杂

```bash
git merge --no-ff release/v1.0.0
```

#### Rebase

- **用途**: 保持线性历史
- **优点**: 历史清晰
- **缺点**: 可能改变历史

```bash
git rebase develop
```

## 版本号命名规则

### 语义化版本

遵循 [Semantic Versioning 2.0.0](https://semver.org/) 规范。

#### 版本格式

```
MAJOR.MINOR.PATCH
```

#### 版本规则

| 变化 | 版本部分 | 示例 |
|------|---------|------|
| 不兼容的 API 变化 | MAJOR | 1.0.0 → 2.0.0 |
| 向后兼容的功能新增 | MINOR | 1.0.0 → 1.1.0 |
| 向后兼容的问题修复 | PATCH | 1.0.0 → 1.0.1 |

#### 预发布版本

```
MAJOR.MINOR.PATCH-PRERELEASE
```

示例：
- `1.0.0-alpha`
- `1.0.0-alpha.1`
- `1.0.0-beta`
- `1.0.0-beta.1`
- `1.0.0-rc.1`

#### 构建元数据

```
MAJOR.MINOR.PATCH+BUILD
```

示例：
- `1.0.0+20130313144700`
- `1.0.0-beta+exp.sha.5114f85`

### 版本标签

#### 创建标签

```bash
# 创建轻量标签
git tag v1.0.0

# 创建带注释的标签
git tag -a v1.0.0 -m "Release version 1.0.0"

# 推送标签到远程
git push origin v1.0.0

# 推送所有标签
git push origin --tags
```

#### 标签命名规范

- 使用 `v` 前缀
- 遵循语义化版本
- 使用小写字母

示例：
- `v1.0.0`
- `v1.1.0`
- `v2.0.0-alpha`
- `v2.0.0-beta.1`

### 版本发布流程

#### 1. 创建 release 分支

```bash
git checkout develop
git pull origin develop
git checkout -b release/v1.0.0
```

#### 2. 更新版本号

更新 `go.mod` 文件中的版本号：

```go
module github.com/purpose168/bubbletea-cn

go 1.24.2
```

#### 3. 更新 CHANGELOG

更新 `CHANGELOG.md` 文件：

```markdown
## [1.0.0] - 2024-01-01

### Added
- 初始版本发布
- 实现核心功能
```

#### 4. 提交和合并

```bash
# 提交更改
git add .
git commit -m "chore: 准备发布 v1.0.0"

# 合并到 main
git checkout main
git merge --no-ff release/v1.0.0

# 合并到 develop
git checkout develop
git merge --no-ff release/v1.0.0

# 创建标签
git tag -a v1.0.0 -m "Release version 1.0.0"

# 推送
git push origin main
git push origin develop
git push origin v1.0.0
```

#### 5. 发布到 GitHub

在 GitHub 上创建 Release：
- 选择标签 `v1.0.0`
- 填写发布说明
- 上传构建产物

## 提交信息规范

### 提交信息格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 提交类型

| 类型 | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `docs` | 文档更新 |
| `style` | 代码格式（不影响功能） |
| `refactor` | 重构（不是新功能也不是修复） |
| `perf` | 性能优化 |
| `test` | 添加测试 |
| `chore` | 构建过程或辅助工具的变动 |
| `ci` | CI 配置文件和脚本的变动 |
| `revert` | 回退先前的提交 |

### 提交示例

#### 功能提交

```
feat(renderer): 添加 ANSI 压缩功能

添加 ANSI 压缩功能以减少输出大小，提高性能。

- 实现压缩算法
- 添加压缩选项
- 更新文档

Closes #123
```

#### 修复提交

```
fix(input): 修复 Unicode 字符输入问题

修复 Unicode 字符输入时可能出现的乱码问题。

- 修正字符编码处理
- 添加测试用例

Fixes #456
```

#### 文档提交

```
docs(readme): 更新安装说明

更新 README 中的安装说明，添加新的依赖信息。
```

#### 重构提交

```
refactor(renderer): 重构渲染器代码

重构渲染器代码以提高可维护性。

- 提取公共方法
- 优化代码结构
```

## 分支保护规则

### main 分支保护

- **要求**: 必须通过代码审查
- **要求**: 必须通过 CI 检查
- **要求**: 必须通过状态检查
- **限制**: 只有维护者可以推送
- **限制**: 禁用强制推送

### develop 分支保护

- **要求**: 必须通过代码审查
- **要求**: 必须通过 CI 检查
- **限制**: 只有维护者可以推送

## 代码审查规范

### 审查检查清单

- [ ] 代码实现了预期的功能
- [ ] 代码遵循项目规范
- [ ] 代码有充分的测试
- [ ] 代码有适当的注释
- [ ] 代码没有安全漏洞
- [ ] 代码没有性能问题
- [ ] 提交信息清晰准确

### 审查流程

1. 提交 Pull Request
2. 自动运行 CI 检查
3. 至少一名维护者审查代码
4. 审查者提出修改意见
5. 作者修改代码
6. 审查通过后合并

## 回退策略

### 回退提交

```bash
# 回退单个提交
git revert <commit-hash>

# 回退多个提交
git revert <commit-hash1> <commit-hash2>

# 回退合并提交
git revert -m 1 <merge-commit-hash>
```

### 回退发布

```bash
# 回退到上一个版本
git checkout v1.0.0
git checkout -b hotfix/v1.0.1

# 修复问题
# ...

# 合并到 main
git checkout main
git merge --no-ff hotfix/v1.0.1

# 创建新标签
git tag -a v1.0.1 -m "Hotfix version 1.0.1"
```

## 持续集成

### GitHub Actions 配置

```yaml
name: CI

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main, develop ]

jobs:
  test:
    runs-on: ubuntu-latest
    
    steps:
    - uses: actions/checkout@v3
    
    - name: Set up Go
      uses: actions/setup-go@v4
      with:
        go-version: '1.24.2'
    
    - name: Install dependencies
      run: go mod download
    
    - name: Format check
      run: |
        go fmt ./...
        if [ -n "$(gofmt -l .)" ]; then
          echo "Go code is not formatted:"
          gofmt -d .
          exit 1
        fi
    
    - name: Vet
      run: go vet ./...
    
    - name: Test
      run: go test -v -race -cover ./...
    
    - name: Build
      run: go build -v ./...
```
